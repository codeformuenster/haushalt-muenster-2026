Summary

The code is carefully commented and accessible, and almost nothing in it is overengineered. The real cost is duplication. The same domain fact, such as an Ergebnisplan row index or the name of a Produktbereich, is defined in several files and often worded differently in each. Every copy is a place where a later change can be forgotten.

The second problem is size. Three pages have more than 1,000 lines each and hold data loading, aggregation, chart options, screen-reader plumbing and 300 lines of CSS in one file. The third is the data pipeline. App data is produced in four places in two languages, and only part of the chain runs from the build script.

Most of the gain comes from about ten small shared modules and from deleting one redundant preprocessing path. Splitting the big pages is easier after that, because much of their content moves into the shared modules.

A. One source per fact

The app reads the same budget figures from several files. When a page needs a value, the author picked whichever source was nearest. The result is drift: the same Produktbereich has four different names, and the same row is addressed by a number in one file and by its label in another.

A1. Ergebnisplan row indices

Six files define their own way to address rows of planspiel.json. Three use a constant map, one uses bare numbers, two look up the label at runtime. The maps overlap but are not identical, so a reader cannot tell which is authoritative.

Suggestion. Create src/data/ergebnisplan.ts with one complete ZEILE map, a type Jahr = '2026' | '2027', and the accessors gesamt(jahr, zeile), produktgruppe(code, jahr, zeile) and bereichSumme(code, jahr, zeile). The accessors in karten.ts are fixed to 2026 today; the new ones take the year as a parameter. Also affected: UeberblickPage.vue:18, EinAusgabenAufwandsarten.vue:28.

A2. The same figures in CSV and JSON

Two scripts in preprocessing/ reshape the Gesamtübersicht CSV into two committed CSVs under src/assets/data/. data/einAusgaben.ts parses them with a 50-line hand-written CSV parser. Both review agents checked that Erträge, Aufwendungen and Ergebnis per Produktgruppe are identical to planspiel.json rows 10, 17 and 26 (one checked all 68 Produktgruppen for 2026). Only the four investment columns are new. StartPage.vue:10 imports a third copy of the data straight from ../../../daten/agg_tables/ and has its own copy of the CSV parser (StartPage.vue:66-118).

Suggestion. Add EinzInvest and AuszInvest per Produktgruppe to planspiel.json in planspiel_daten.py, which already loads the Gesamtübersicht. Then delete preprocess_gesamtuebersicht.py, extract_gesamtuebersicht_gruppen.py, both CSVs and both app-side CSV parsers. StartPage takes its totals from planspiel.json as well.

B. Data pipeline

The Python code in scripts/pipeline is in good shape. It has a shared helper (rohdaten.py), one script per source section, and checks against the sum rows printed in the PDF. The complexity sits around it. App data is produced in four places: scripts/pipeline, preprocessing/*.ts, preprocessing/*.py and vue-project/scripts. Each has its own language, path convention and validation style, and the dependency chain between them is manual.

Each step is small enough for one pull request. Later steps get easier because earlier ones remove copies.
